My loop for new projects is deliberately boring.

1. **Capture as beads.** Every idea, bug and chore becomes an issue in [beads](https://github.com/steveyegge/beads), which stores issues in the repo itself, next to the code, with real dependencies between them.
2. **Let the graph decide.** `bd ready` lists only the tasks with no open blockers. That is the whole scheduler.
3. **Run a herd.** With herdr and ntm I keep several agent panes open side by side, each claiming one ready bead, so the work fans out and the dependency graph keeps it honest.
4. **Review and merge.** My job is steering and taste: reading diffs, playtesting builds, and writing the next beads.

On the bigger projects the agents also coordinate with each other. Each one registers with MCP Agent Mail under a name, reserves the files it is about to edit, and announces its claim in a thread named after the bead. The swarm stays small on purpose: five ntm panes at most, including mine, with idle panes reused as worker, validator or release manager rather than adding more agents. Newer projects use `br` (beads in Rust) and `bv --robot-next` to ask the graph what matters most.

## What it looks like in practice

These are real beads from this repository:

```bash
bd create "Terminal dock-spawn animation from navbar" --type feature --priority 2
bd dep add ghost-blog-0tt ghost-blog-cog   # sequenced after the particle mask transition
bd ready                                   # what can an agent pick up right now?
bd update ghost-blog-0tt --status in_progress
bd close ghost-blog-0tt --reason "Terminals spawn from navbar with elastic easing."
bd sync                                    # issues travel with git
```

Each agent session starts with `bd ready`, claims one bead, and ends by closing it with the evidence. No re-briefing. The plan is in the repo, so a fresh session picks up exactly where the last one stopped.

## Real numbers: the site before this one

The previous Ghost theme for this site was planned and built this way over about ten days in January 2026. The beads database is still in the repository, so here is what that looked like.

- **99 beads**: 62 tasks, 28 features, 5 bugs and 4 epics.
- **133 dependency links** between them. 42 beads were blocked by at least one other, and one waited on ten.
- **85 closed** by the end; the 14 still open were deliberately parked ideas, not forgotten work.

## Why the graph matters more than the agents

The part that surprised me is how much the graph helps *me*. Writing the plan down as small, dependent pieces forces the thinking up front, and it makes the agents interchangeable: any of them can take the next ready bead. When something goes wrong, the fix is usually a better bead (clearer acceptance criteria, a missing dependency), not a better prompt. I wrote about that shift in [Your Prompts Do Not Matter (Anymore)](/blog/your-prompts-do-not-matter-anymore/).
